이번 모듈은 "내 컴퓨터에서 돌아가는 코드"를 "손님이 쓰는 서비스"로 바꾸는 과정이었다. 2주 동안 AI 친구
서비스(friend-agent)를 PR 43개로 고쳐 올렸다. 내 투자 서비스인 FA 여정 체험판은 올린 첫날에만 버전(리비전)이
22개 쌓였다.

다 끝나고 돌아보니 배운 것이 한 문장으로 줄었다. **"배포 성공"은 아무것도 보장하지 않는다.** 앱이 켜졌다는
뜻일 뿐, 맞게 동작한다는 뜻이 아니었다. 이번 모듈에서 배운 기술은 전부 이 틈을 메우는 장치였다.

![이번 모듈 전체 요약]({{ site.baseurl }}/assets/2026-10-30-service-deploy/all.gif)
*이번 모듈 전체 53초 요약*

용어가 너무 많아서 처음엔 식당에 빗대어 외웠다.

| 배운 것 | 식당으로 말하면 |
|---|---|
| 서비스 설계 | 무엇을, 누구에게, 언제 낼지 정하기 |
| Cloud Run | 손님이 오면 불을 켜고, 없으면 끄는 매장 |
| CI/CD | 레시피를 바꾸면 시식 → 2호점 → 본점 순서로 자동 납품 |
| Docker | 주방 도구까지 통째로 담은 밀키트 — 어느 지점에서 끓여도 같은 맛 |
| 블루그린·카나리·롤백 | 새 메뉴는 손님 10%에게 먼저 내고, 이상하면 바로 옛 메뉴로 |

![식당으로 말하면]({{ site.baseurl }}/assets/2026-10-30-service-deploy/restaurant.gif)
*배운 것을 식당에 빗대면*

배운 순서대로, 각 단계에서 실제로 무엇이 터졌는지를 적어 본다.

## 1. 서비스 설계 — LLM을 "어디에 두지 않을지"부터

![AI 기능을 서비스로 설계하기]({{ site.baseurl }}/assets/2026-10-30-service-deploy/design.gif)
*AI 기능을 서비스로 설계하기*

첫날에는 FA 자동매매를 서비스로 설계했다. 사용 맥락 표를 채우자마자 핵심이 보였다. 미국장 마감(새벽
04:40~06:10)에 사용자는 자고 있다. 그래서 처리 방식은 **스케줄 실행**이고, 결과는 아침에 텔레그램으로
받는다.

그다음 질문은 "AI를 어디에 넣을까"가 아니라 **"어디에 넣지 말까"**였다. 매매 판단은 규칙이 하고, LLM은
결과를 설명하는 데만 쓴다. 틀렸을 때 피해가 큰 자리에는 LLM을 두지 않았다.

시퀀스 다이어그램을 그려 보니 화살표 대부분이 실패에 대비하는 것이었다. 실행 시각 확인, 체결 재확인, 대체
알림이다. F&G 30 아래로 떨어지는 매수 기회는 1년에 두세 번뿐이라서, 한 번 빠지면 다음 기회까지 몇 달을
기다려야 한다.

> 설계는 한 번으로 끝나지 않았다. FA 여정 첫 화면을 아내에게 보여 줬더니 "투자 방법 찾는 앱은 많은데,
> 너무 단순해서 매력이 없다"고 했다. 그래서 첫 화면을 질문 대신 **28년 동안의 실제 결과**로 바꿨다.
> 2009년 3월 −41.5% 지점에 "여기서 팔지 않고 기다렸어요"라는 표시를 넣었다. 사용자에게 바라는 행동이
> 하나(기다리기)라면, 첫 화면도 그것 하나를 보여 줘야 했다.

## 2. Cloud Run — 오류 메시지는 결과, 원인은 그 위 한 줄

![Cloud Run으로 배포하기]({{ site.baseurl }}/assets/2026-10-30-service-deploy/cloudrun.gif)
*Cloud Run으로 배포하기*

첫 배포는 일부러 AI 키 없이 올려서 실패시켰다. 터미널에는 "포트 8080에서 시작하지 못했다"고 떴다. 그런데
로그를 열어 보니 **그 1초 전**에 진짜 원인이 있었다.

```
14:35:04 ERROR LLM_API_KEY 환경변수가 없어 앱을 시작하지 않습니다.
14:35:05 ERROR STARTUP TCP probe failed … on port 8080
```

메시지만 믿고 포트 설정을 고쳤다면, 멀쩡한 설정만 바꾸면서 계속 실패했을 것이다. 이후로는 에이전트에게도
"로그를 근거로 원인부터 말해 줘, 아직 고치지 마"라고 먼저 부탁한다.

FA 여정에서도 비슷한 일이 있었다. 분명히 고쳐서 배포했는데 화면이 그대로였다. 서버가 주는 파일을 직접 받아
보니 새 코드가 들어 있었다. 응답 머리에는 `last-modified: 1980-01-01`이 찍혀 있었다. 빌드할 때 파일 시각이
1980년으로 바뀌어서, 브라우저가 "아주 오래된 파일"로 보고 서버에 다시 묻지 않은 것이다. 서버 문제가
아니라 **브라우저 캐시** 문제였다.

운영 설정 값도 짐작이 아니라 측정으로 정했다.

| 설정 | 정한 값 | 근거 |
|---|---|---|
| 요청 시간 제한 | 60초 | 실측 233건: 중간값 0.05초, 느린 쪽 5%(p95) 0.13초 |
| 인스턴스 수 | 최소 0, 최대 2 | 체험판이라 안 쓸 땐 0원, 몰려도 상한이 있음 |

## 3. CI/CD — "머지했으니 배포됐겠지"는 없다

![CI/CD]({{ site.baseurl }}/assets/2026-10-30-service-deploy/cicd.gif)
*CI/CD*

GitHub Actions로 "머지하면 자동 배포"를 만들었다. 배포 권한은 키 파일 대신 Workload Identity Federation(WIF)으로
줬다. 매번 1시간짜리 토큰을 받고, **내 저장소에서 온 요청만** 통과한다. 다른 저장소에 같은 코드를 넣고 돌려
보니 11초 만에 인증 단계에서 거절됐다.

자동 배포가 생기자 오히려 무서운 일이 생겼다. "약속 시각 저장 형식 단순화" PR이 **배포에 성공했는데**,
"내일 아침 8시에 알려 줘"가 **17:00**으로 저장됐다. 서버는 UTC 시간대, 내 PC는 한국 시간이었다. 앱은 잘
켜졌으니 배포 검사로는 걸러지지 않았다.

다음 날 CI 테스트를 붙이고 같은 버그를 다시 넣어 봤다.

| 어디서 돌렸나 | 결과 | 이유 |
|---|---|---|
| 내 PC (한국 시간) | 11개 모두 통과 | 시간대가 빠진 시각이 우연히 한국 시간으로 읽힘 |
| CI 러너 (UTC) | 1개 실패: `08:00` 대신 `17:00` | 서버와 같은 환경이라 버그가 드러남 |

원래 있던 테스트는 "시간대 정보가 붙어 있나"만 봤다. 그래서 버그가 있어도 통과했다. **사용자가 보는
`08:00`을 확인해야** 버그가 잡혔다. 그 뒤로 일부러 넣은 버그 세 개(위기 안내 누락, 날씨 도구 미호출, 시간대)는
CI가 모두 막았다. 브랜치 보호를 걸어 두니 머지 버튼 자체가 잠겼다.

다만 CI도 만능은 아니었다. "보내기 버튼 스타일 정리" PR은 테스트를 통과했지만, staging 화면에서 **보내기
버튼이 사라져 있었다.** 이건 사람 눈이 staging에서 잡았다. 그래서 운영 배포 앞에는 사람이 누르는 승인 버튼을
뒀다.


## 4. Docker — "내 PC에선 되는데"를 끝내는 법

![Docker]({{ site.baseurl }}/assets/2026-10-30-service-deploy/docker.gif)
*Docker*

사진 속 일정을 읽는 기능(OCR)을 켜자 staging에서 500 오류가 났다. 로그에는 "tesseract 프로그램을 찾을 수
없습니다"라고 나왔다. 자동 빌드(buildpacks)는 파이썬 버전과 라이브러리는 챙기지만, **운영체제에 깔아야 하는
프로그램**은 모른다. 실행 환경 전체를 Dockerfile 한 파일에 적고 나서야 내 PC, staging, 운영 세 곳이 같은
결과를 냈다.

```dockerfile
FROM python:3.13-slim-bookworm
RUN apt-get update \
 && apt-get install -y --no-install-recommends tesseract-ocr tesseract-ocr-kor \
 && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
RUN useradd --create-home appuser
USER appuser
CMD ["sh", "-c", "uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8080}"]
```

여기서 한 걸음 더 나간 것이 **"이미지는 한 번만 빌드한다"**는 원칙이었다. `requirements.txt`가
`anthropic>=1.15`처럼 "이상"으로 적혀 있으면, 빌드할 때마다 그 순간의 최신 버전이 들어간다. 그러면 staging에서
확인한 것이 운영을 보장하지 못한다.

그래서 staging에서 만든 이미지를 그대로(다이제스트, 즉 내용의 지문으로 지정해서) 운영에 올리게 바꿨다. 효과는
숫자로 바로 보였다.

- 되돌릴 버전 찾기: 만든 시각을 맞춰 보며 짐작하던 것이 **커밋 태그로 6초**가 됐다.
- 운영 배포: 다시 빌드하지 않으니 **1분 26초에서 41초**로 줄었다.

고장 난 Dockerfile 네 개를 고치는 실습에서 가장 무서웠던 건 **root로 실행되는 이미지**였다. 서비스는 완전히
정상으로 돌아서, 일부러 들여다보지 않으면 절대 모른다. 오류가 나는 고장보다 정상처럼 보이는 고장이 더
위험하다는 걸 여기서도 느꼈다.

## 5. 배포 전략 — 일부러 망가뜨려 보기

![서비스 배포 전략 1일차 · Nginx 실험]({{ site.baseurl }}/assets/2026-10-30-service-deploy/lb.gif)
*서비스 배포 전략 1일차 · Nginx 실험*

마지막 이틀은 "새 버전으로 바꾸는 그 순간"을 다뤘다. 먼저 내 컴퓨터에서 Nginx로 로드밸런서를 직접 만들었다.

| 실험 | 실패한 요청 | 배운 것 |
|---|---|---|
| blue → green 전환 (설정 한 줄 + reload) | 78건 중 0건 | 하던 요청을 마치고 넘긴다 |
| green을 갑자기 끔 (기본 설정) | 9건 | 실제 요청이 실패해야 고장을 알아챈다 |
| 같은 실험, 연결 대기 1초 | 264건 중 0건 | 대신 그 요청은 1초 늦는다 |

그런데 실패가 0건이어도 **대화가 사라졌다.** 대화를 컨테이너 메모리에 두었기 때문이다. 대화를 데이터베이스
(Supabase)로 옮기자 전환해도, 재시작해도 대화가 이어졌다. 이게 이번 모듈의 정의가 됐다.

> **무중단 = 요청이 안 끊김 + 하던 일이 이어짐.** 둘 중 하나만 보면 다른 쪽 고장을 놓친다.


그다음 Cloud Run에서 같은 일을 자동으로 하게 만들었다. 지금 운영 배포는 아래 길을 지난다.

![운영 배포 파이프라인]({{ site.baseurl }}/assets/2026-10-30-service-deploy/diagram-pipeline.svg)

여기서도 일부러 망가뜨렸다.

**① 켜지는 데 느린 버전.** 시작 검사가 "포트가 열렸나"만 보면, 앱이 준비되기 전에 손님을 받아서 324건 중
63건이 실패했다. "`/health`가 정상이라고 답하나"를 보게 하니 377건 중 0건이 됐다.

**② 켜지긴 하는데 느린 버전.** `/version`이 1.5초 늦게 답하게 일부러 만들어 올렸다. 손님 10%만 받는 첫
단계에서 새 버전의 느린 쪽 응답(p95)이 1.58초로 재졌다. 기존 버전은 0.08초였다. 워크플로가 스스로 판단해
**이전 버전으로 100% 되돌렸고**, 나머지 90% 손님은 아무 일도 몰랐다.

```bash
for P in 10 50; do
  gcloud run services update-traffic "$SERVICE" --to-revisions "$NEW=$P,$OLD=$((100 - P))"
  if ! python3 scripts/canary_check.py "$URL" "$NEW" "$OLD" --seconds 120; then
    gcloud run services update-traffic "$SERVICE" --to-revisions "$OLD=100"   # 자동 롤백
    exit 1
  fi
done
```

![카나리 자동 판단]({{ site.baseurl }}/assets/2026-10-30-service-deploy/canary.gif)
*서비스 배포 전략 2일차 · 10%에서 느린 버전을 잡아 자동 롤백*


손으로 누르는 롤백 버튼도 만들었다. 승인하고 25초 만에 이전 버전으로 돌아갔다. 이 자동 카나리로 실제 운영에
배포하는 동안 요청 1,035건(다른 측정 방식으로 2,089건)을 보냈는데 실패는 0건이었다.

## 6. FABOT에 옮긴다면

![FABOT에 옮긴다면]({{ site.baseurl }}/assets/2026-10-30-service-deploy/fabot.gif)
*FABOT에 옮긴다면*

배우는 내내 FABOT 자동매매에서 겪었던 사고가 겹쳐 보였다. 이미 넣은 것도 있고, 이제 넣어야 할 것도 있다.

| 이번 모듈에서 배운 것 | FABOT에서 실제로 겪은 일 | 옮길 것 |
|---|---|---|
| 배포 성공 ≠ 맞는 동작 → 스모크 테스트 | 09-18 F&G 29 신호. GitHub Actions는 "success"였는데 키움 계좌는 TQQQ를 사지 않았다 | 주문 뒤 잔고를 다시 조회해 대조하는 **체결 스모크 테스트** (다음 과제) |
| 시작 검사: 준비된 것에만 손님을 보낸다 | 08-28 정해진 시각이 아닌 12:53에 매수가 실행됐다 | "지금이 마감 실행 시간대인가" 확인 장치 (**적용함**, 08-31) |
| 이미지는 한 번만 빌드한다 | 한국투자증권(KIS)·키움 스크립트가 따로 있다. 09-17에 KIS 쪽 버그를 고쳤지만, 키움 쪽이 따로 막혀 있던 건 다음 날 매수가 빠지고서야 알았다 | 매매 규칙 코드를 하나로 두고 증권사 연결만 나누기 (다음 과제) |
| 카나리: 일부에만 먼저 | 분기마다 매매 기준값을 다시 찾는데, 지금은 찾은 값을 한 번에 적용한다 | 새 기준값은 모의계좌(staging)에서 먼저 돌리고, 기준을 넘으면 이전 값으로 (구상) |
| 무상태: 상태는 서버 밖에 | 매수 쉬는 기간(쿨다운) 계산이 매매 기록에 달려 있다 | 기록은 이미 Supabase에 있음. 기록이 빠지면 계산이 틀어진다는 점을 감시하기 |

첫 줄이 가장 아프다. "로그는 성공인데 실제로는 안 샀다"는 건, 이번 모듈 첫 주에 겪은 "배포는 성공인데

## 정리

![정리]({{ site.baseurl }}/assets/2026-10-30-service-deploy/summary.gif)
*정리*

다섯 단원을 다시 놓고 보면, 매번 같은 질문을 한 칸씩 더 앞당겼다.

- **Cloud Run:** 켜졌나? (시작 검사)
- **CI/CD:** 맞게 동작하나? (테스트)
- **Docker:** 어디서든 똑같이 동작하나? (Dockerfile, 같은 이미지)
- **배포 전략:** 손님에게 내보내는 순간에도 괜찮은가? (카나리, 롤백)

기술 이름은 다 달랐지만, 결국 **"확인할 자리"를 하나씩 더 만드는 일**이었다. 식당으로 말하면 맛있는 레시피를
만드는 것보다, 맛이 이상할 때 손님 대부분이 먹기 전에 알아채는 구조를 만드는 게 장사를 오래 하는 법이었다.

아직 남은 빈칸도 있다. 운영에서 버전을 바꾸는 순간에 요청 몇 건이 시간 초과로 실패한 적이 한 번 있었다.
이후 두 번의 운영 배포에서는 0건이었지만, 원인은 끝내 찾지 못했다. 다음 운영 배포 때도 같은 측정을 다시
걸어 둘 생각이다. "재현이 안 되니 괜찮다"는 이번 모듈에서 배운 것과 가장 거리가 먼 결론이기 때문이다.
